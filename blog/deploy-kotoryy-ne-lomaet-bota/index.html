Деплой, который не ломает бота: тесты до подъема, а не после

2026-04-23кейс

У меня система из двух контейнеров: веб-сервис и телеграм-бот с планировщиком. Код лежит внутри образа, а не в подключенном каталоге - то есть контейнер не смотрит в папку на сервере, где файл можно поправить на месте и перезапустить процесс. Из-за этого любая правка, даже в одну строку, означает пересборку образа. Точки «поправить на живую» просто нет.

Это звучит как неудобство, но на самом деле это подарок: раз выкладка все равно всегда одна и та же процедура, ее можно один раз выстроить так, чтобы сломанная версия физически не доезжала до пользователей. К концу статьи вы получите этот порядок шагов и поймете, почему быстрый путь в обход тестов обходится дороже, чем кажется в момент, когда вы его выбираете.

Соблазн быстрой выкладки

Быстрый путь - это одна команда: пересобрать и поднять. Она есть почти в любом проекте, и она обходит тесты целиком. Соблазн понятен: правка маленькая, полный цикл идет дольше, а «тут нечего ломать».

Проблема в том, что у бота нет страницы с ошибкой. Веб-сервис, который не поднялся, виден сразу - кто-то откроет и увидит. Бот, который не поднялся, выглядит как молчание: пользователь пишет и не получает ответа, а планировщик просто не делает работу в назначенное время. Никто не получает сообщение об ошибке, потому что сообщать некому - процесс не запустился.

Поэтому у меня быстрый путь существует, но он не режим работы, а исключение. Он нужен для срочной заплатки, когда что-то горит прямо сейчас. И он оставляет долг: после него обязательно прогоняется полный цикл. Если долг не отдать, вы получаете сервер, про который никто не знает, проходят ли на нем тесты, - и следующая выкладка будет ремонтировать сразу две проблемы вместо одной.

Порядок, который защищает: тесты до подъема

Полный цикл - это четыре шага строго в таком порядке:

  • синхронизация файлов на сервер
  • сборка образов
  • прогон модульных тестов в отдельном одноразовом контейнере
  • подъем рабочих контейнеров

Одноразовый контейнер - это контейнер, который поднимается из свежесобранного образа, выполняет одну задачу и умирает, не оставаясь в работе. Тесты гоняются именно в нем: в той же среде, что и продакшн, но без последствий.

Весь смысл - в том, что третий шаг стоит перед четвертым. Если тесты падают, до подъема дело не доходит. На сервере продолжает работать предыдущая версия - та самая, которая вчера работала. Пользователь не видит ничего, потому что для него ничего и не произошло. Это принципиально другое поведение, чем «подняли, увидели ошибку, откатились»: между «подняли» и «увидели» всегда есть окно, и в этом окне бот молчит.

Почему именно до, а не после

Есть и вторая причина, менее очевидная. Мои тесты открывают ту же базу знаний, что и рабочий процесс. Когда я запускала их поверх уже поднятых контейнеров, возникала гонка - ситуация, когда два процесса лезут в один ресурс одновременно и результат зависит от того, кто успел первым. Тест мог упасть не потому, что код плохой, а потому, что в тот момент к базе обратился живой бот.

Падающий через раз тест - худший вид теста: ему перестают верить, а потом перестают смотреть. Порядок «тесты до подъема» убирает гонку без единой строчки кода: в момент прогона рабочие контейнеры еще не запущены, конкурировать не с кем.

Проверка после подъема и ее границы

После подъема скрипт ждет, пока сервис ответит, что готов. Здесь два правила, каждое из которых я узнала не из документации.

Ожидание должно быть ограничено по времени. Без ограничения скрипт выкладки однажды висел бесконечно - он ждал ответа, которого уже не будет. Хуже всего не то, что версия сломана, а то, что выкладка не заканчивается ни успехом, ни провалом, и вы не знаете, в каком состоянии система. Ограничение превращает зависание в честный отрицательный результат, с которым можно что-то делать.

Проверка готовности должна быть дешевой. У меня обработчик, отвечающий на вопрос «ты жив?», лез за статистикой базы. Пока база отвечала быстро, все было прекрасно. Когда база подвисала, обработчик подвисал вместе с ней, ожидание упиралось в ограничение по времени, и выкладка ложно считалась неудачной - хотя сервис был поднят и работал.

Проверка готовности отвечает ровно на один вопрос: процесс поднялся и принимает запросы. Она не отвечает на вопрос «все ли хорошо в системе». Как только вы начинаете подмешивать в нее содержательные проверки, она наследует все их способы сломаться.

Отсюда ее границы. Проверка после подъема ловит «не поднялось». Она не ловит «поднялось, но считает неправильно» - это работа тестов, которые прошли раньше. Не пытайтесь закрыть вторым инструментом то, что должен был поймать первый.

Что не должно уезжать вместе с кодом

Отдельная категория граблей - синхронизация файлов с удалением лишнего. Такая синхронизация приводит каталог на сервере к состоянию репозитория: копирует новое и заодно стирает все, чего в репозитории нет.

Однажды она стерла у меня рабочий конфиг с плановыми показателями. Файл был нужен системе, но его не было в репозитории - и с точки зрения синхронизации он был мусором. Формально все отработало правильно. Фактически я потеряла данные, которые существовали в одном экземпляре.

Вывод простой: все, что живет только на сервере, должно быть в списке исключений. Как минимум:

  • файлы окружения с секретами
  • каталоги баз данных
  • журналы
  • пользовательские данные

Полезно держать в голове разделение: репозиторий владеет кодом, сервер владеет состоянием. Код едет с машины разработчика на сервер и может быть перезаписан без сожалений - он воспроизводится из истории. Состояние рождается на сервере и не воспроизводится ниоткуда. Если файл создается или меняется в процессе работы системы, он не собственность репозитория, и синхронизация не имеет права его трогать.

Применить у себя

Что проверить на практике

  • Найдите в своих скриптах быстрый путь и посмотрите, обходит ли он тесты. Если да - переименуйте его так, чтобы имя честно говорило, что это аварийный режим.
  • Разложите выкладку на четыре шага и убедитесь, что падающие тесты действительно останавливают скрипт. Проверяется это тем, что тестовый шаг возвращает ненулевой код, а скрипт на нем прерывается, а не идет дальше.
  • Проверьте, что тесты идут до подъема рабочих контейнеров и не делят состояние с живым процессом. Если тесты и продакшн открывают одно хранилище - порядок шагов это уже лечит.
  • Откройте обработчик проверки готовности и посмотрите, куда он ходит. Если он читает базу, считает записи или собирает статистику - уберите это оттуда.
  • Найдите место, где скрипт ждет готовности, и убедитесь, что у ожидания есть ограничение по времени. Потом испытайте его: выложите заведомо нерабочую версию и посмотрите, закончится ли скрипт сам.
  • Выпишите список всего, что живет только на сервере, и сверьте его со списком исключений синхронизации. Перед реальным прогоном запустите синхронизацию в режиме dry-run - «показать, что будет сделано, но ничего не делать» - и прочитайте список файлов, помеченных к удалению.

Как понять, что получилось

Выкладка настроена правильно, если выполняются все пять условий:

  • Вы намеренно ломаете один тест, запускаете полный цикл - и рабочие контейнеры не перезапускаются. На сервере продолжает жить старая версия, пользователи ничего не заметили.
  • Выкладка всегда заканчивается: либо успехом, либо явной неудачей с понятной причиной. Состояния «висит уже десять минут» не существует.
  • Подтормаживающая база не делает выкладку неудачной. Проверка готовности говорит только про сам процесс.
  • dry-run синхронизации не показывает к удалению ни одного файла, который вам нужен.
  • После каждого использования аварийного быстрого пути полный цикл был прогнан, и вы можете сказать, когда именно.

Если свести все к одной фразе: тесты до подъема, ожидание с ограничением, дешевая проверка готовности и честный список исключений. Четыре решения, каждое из которых стоит один вечер, - и сломанная версия перестает быть событием для пользователей.

Tests Before Startup: Four Decisions That Keep a Broken Version Off the Server

2026-04-23case

I have a system of two containers: a web service and a Telegram bot with a scheduler. The code lives inside the image, not in a mounted directory - meaning the container doesn't look at a folder on the server where you could patch a file in place and restart the process. Because of that, any edit, even a one-liner, means rebuilding the image. There simply is no "fix it live" spot.

That sounds like an inconvenience, but it's actually a gift: since deployment is always the exact same procedure anyway, you can build that procedure once so that a broken version physically cannot reach users. By the end of this article you'll have that sequence of steps, and you'll understand why the fast path around the tests costs more than it looks like at the moment you choose it.

The temptation of the fast deploy

The fast path is a single command: rebuild and bring it up. It exists in almost every project, and it skips the tests entirely. The temptation is understandable: the edit is small, the full cycle takes longer, and "there's nothing here to break."

The problem is that a bot has no error page. A web service that failed to start is visible immediately - someone opens it and sees it. A bot that failed to start looks like silence: the user writes and gets no answer, and the scheduler just doesn't do its work at the appointed time. Nobody gets an error message, because there's no one to send it - the process never started.

So the fast path does exist for me, but it's not a working mode, it's an exception. It's there for an urgent patch when something is on fire right now. And it leaves a debt: afterwards the full cycle gets run, no exceptions. If you don't pay that debt, you end up with a server nobody knows the test status of - and the next deploy will be repairing two problems instead of one.

The order that protects: tests before startup

The full cycle is four steps, strictly in this order:

  • syncing files to the server
  • building the images
  • running the unit tests in a separate throwaway container
  • bringing up the working containers

A throwaway container is a container that starts from the freshly built image, does one job, and dies without staying in service. That's exactly where the tests run: in the same environment as production, but without consequences.

The whole point is that step three comes before step four. If the tests fail, it never gets to startup. The previous version keeps running on the server - the one that worked yesterday. The user sees nothing, because as far as they're concerned nothing happened. This is fundamentally different behavior from "brought it up, saw the error, rolled back": between "brought it up" and "saw" there is always a window, and in that window the bot is silent.

Why before, and not after

There's a second reason, less obvious. My tests open the same knowledge base as the working process. When I ran them on top of already-running containers, a race appeared - the situation where two processes reach for the same resource at once and the result depends on who got there first. A test could fail not because the code was bad, but because at that moment the live bot hit the base.

A test that fails every other time is the worst kind of test: people stop believing it, and then stop looking at it. The "tests before startup" order removes the race without a single line of code: at the moment of the run, the working containers aren't up yet, so there's nothing to compete with.

The post-startup check and its limits

After startup, the script waits until the service reports that it's ready. There are two rules here, and I learned each of them somewhere other than the documentation.

The wait must be bounded in time. Without a bound, the deploy script once hung forever - it was waiting for an answer that was never coming. The worst part isn't that the version is broken, it's that the deploy ends in neither success nor failure, and you don't know what state the system is in. A bound turns a hang into an honest negative result, which is something you can act on.

The readiness check must be cheap. My handler, the one answering the question "are you alive?", went and fetched database statistics. As long as the database answered fast, everything was lovely. When the database stalled, the handler stalled with it, the wait ran into its time bound, and the deploy was falsely counted as failed - even though the service was up and running.

A readiness check answers exactly one question: the process started and is accepting requests. It does not answer the question "is everything fine in the system." The moment you start mixing substantive checks into it, it inherits every way those checks can break.

Hence its limits. The post-startup check catches "didn't come up." It doesn't catch "came up but calculates wrong" - that's the job of the tests that ran earlier. Don't try to cover with the second tool what the first one was supposed to catch.

What must not travel with the code

A separate category of rakes is file sync with deletion of extras. That kind of sync brings the directory on the server to the state of the repository: it not only copies what's new, it erases everything the repository doesn't have.

One day it erased my working config with the target metrics. The file was needed by the system, but it wasn't in the repository - and from the sync's point of view it was garbage. Formally, everything worked correctly. In practice, I lost data that existed in exactly one copy.

The conclusion is simple: everything that lives only on the server must be in the exclusion list. At a minimum:

  • environment files with secrets
  • database directories
  • logs
  • user data

It's useful to keep this split in mind: the repository owns the code, the server owns the state. Code travels from the developer's machine to the server and can be overwritten without regret - it's reproducible from history. State is born on the server and isn't reproducible from anywhere. If a file is created or changed while the system runs, it isn't the repository's property, and the sync has no right to touch it.

Put it to work

What to check in practice

  • Find the fast path in your own scripts and look at whether it skips the tests. If it does - rename it so the name honestly says this is an emergency mode.
  • Break the deploy into four steps and make sure failing tests actually stop the script. You verify this by checking that the test step returns a non-zero code and that the script aborts on it instead of continuing.
  • Check that the tests run before the working containers come up and don't share state with the live process. If the tests and production open the same storage - the order of steps already cures that.
  • Open your readiness handler and look at where it goes. If it reads the database, counts records, or gathers statistics - take that out of there.
  • Find the place where the script waits for readiness and make sure the wait has a time bound. Then put it to the test: deploy a knowingly broken version and see whether the script finishes on its own.
  • Write out a list of everything that lives only on the server and compare it against the sync exclusion list. Before a real run, run the sync in dry-run mode - "show what would be done, but do nothing" - and read the list of files marked for deletion.

How to tell it worked

The deploy is set up right if all five conditions hold:

  • You deliberately break one test, run the full cycle - and the working containers don't restart. The old version keeps living on the server, users noticed nothing.
  • The deploy always ends: either in success or in an explicit failure with a clear cause. The state "it's been hanging for ten minutes now" does not exist.
  • A sluggish database doesn't make the deploy fail. The readiness check speaks only about the process itself.
  • The sync dry-run shows not a single file you need marked for deletion.
  • After every use of the emergency fast path, the full cycle was run, and you can say exactly when.

To put it all in one sentence: tests before startup, a bounded wait, a cheap readiness check, and an honest exclusion list. Four decisions, each worth one evening - and a broken version stops being an event for users.
